# Cloud preflight

`node src/main.ts cloud --preflight` loads `.env`, checks the presence of manual Google/HMAC/Cloudflare inputs, verifies an active account-owned or user-owned Cloudflare token, discovers the account when unambiguous, matches the site's zone, and checks read access to Pages, Workers, R2, KV, D1, DNS, Access and Tunnels. This command does not generate configuration, modify `.env`, build, or deploy. Ordinary cloud deployment runs these checks before the build or Terraform and then persists generated configuration. `--dry_run` remains offline and does not provision configuration.

The read-only probes do not prove write permissions. Cloudflare's [permission reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/) lists the edit scopes that Terraform still needs. Multiple visible accounts require an explicit account ID. Google console configuration and consent remain manual.

Local validation reports all independent failures together before any provider request: missing manual inputs, short HMAC/JWT secrets, invalid configured account/zone IDs or owner/admin email, incomplete Access/VAPID pairs, invalid VAPID contact URI, and mismatched/malformed P-256 VAPID keys. Terraform account/zone, JWT, Access and VAPID aliases are recognized. The subsequent eight service reads aggregate their denials. Discovery-dependent checks still wait for a valid account and zone. Errors identify variable names and categories without echoing supplied values. Generated-block validation and atomic write failures leave the environment unchanged.

During deployment, after successful probes, generated account/zone IDs, owner email, VAPID keys and a JWT signing secret are persisted in marked `.env` blocks. Existing nonempty file or environment values win, including Terraform signing-key aliases. Partial VAPID pairs fail instead of rotating. When a signing key is missing locally, preflight reads the configured Worker's bindings. An existing remote secret blocks generation: restore its original value or use a deployment path supporting inherited secret bindings (see [staging infrastructure](../../cloud/infra/staging/README.md)). Read-only preflight reports this condition without generating keys. Only a 404 means the Worker does not exist; denied settings access fails closed. No secret values are logged. Tests use synthetic tokens, denied responses and temporary directories.

## Restored credentials — 2026-11-23

The restored file passes the real read-only CLI check and remains byte-for-byte unchanged. Separate read-only account-token introspection confirms an active token and edit permission groups for Pages, Workers, R2, KV, D1, DNS, Access apps/service tokens and Tunnel. Successful reads do not exercise Terraform writes.

Google's token endpoint returned `invalid_grant` for a deliberately impossible code with the restored client credentials, and `invalid_client` with a deliberately invalid secret. No grant or token was issued. Production/staging authorization probes redirected without an immediate configuration error; this does not prove an interactive consent flow or Drive access. These Google probes are audit evidence, not part of the CLI's presence check.

Both deployed routers already bind `AUTH_JWT_SECRET`; its local copy is absent. The check preserved those bindings and did not generate a replacement. Staging Terraform now includes optional inherited JWT/agent bindings even when their local input is null; validation and four mocked-provider tests pass. Access credentials, OAuth credentials and VAPID keys were also left intact. The provider-input blocker is resolved; provisioning and end-to-end acceptance remain separate work.

Access service-token and Tunnel provisioning are still absent from the main Terraform root. Existing deployments must retain their credentials and imported state. This does not claim a two-variable clean-account bootstrap or change live infrastructure.
