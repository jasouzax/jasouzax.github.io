# JAZU

**JAZU** *(JAsouZa User interface)* is a file-authored website system with three purposes:

- **Portfolio** – a central place where recruiters and the public browse the owner's work.
- **Workspace** – the interface where the owner does personal projects and client work.
- **Showcase** – the system itself implements real techniques from several fields (a TypeScript font writer, a build-time timeline layout engine, WebAssembly Linux userland in the browser, signed edge-to-origin APIs, infrastructure as code), so its own behaviour demonstrates the owner's capabilities live.

This repository is generation 12. Nothing in it is specific to one person: owner values (name, domain, email) live in `config.json` and `content/`.

## What is in the box

| Part | What it is | Where |
|---|---|---|
| **Content** | The owner writes plain XML/Markdown/SCSS: pages, projects, events, blogs, themes, plugins, print layouts. Folder names carry no meaning; the root tag does. | `content/` → [content guide](docs/content/README.md) |
| **Engine** | A TypeScript CLI that validates content and generates a fully static, multilingual, SEO-complete website with incremental rebuilds. TSX generators produce HTML *and* a compact JSON tree for instant client-side navigation. | `src/` → [engine](docs/src/engine.md), [web generation](docs/src/web.md) |
| **Themes** | Same DOM, many looks: CSS + generated icon/text fonts + optional canvas script, switched live, with an inline skeleton so no page is ever blank. | [themes](docs/content/theme.md) |
| **Desk** | A desktop-like workspace in the browser (`/desk`, project and blog desks): tiled windows, file manager, editors, and a real BusyBox shell and C programs compiled to WebAssembly, running over a shared virtual filesystem. A visitor's files never leave their browser. | [desk runtime](docs/src/desk.md) |
| **Cloud** | Static files on Cloudflare Pages; one Worker routes subdomains, large media (R2) and a versioned JSON API; D1/KV hold data. Everything is provisioned by Terraform. The site keeps working if every owner-run server is offline. | [nodes](docs/src/node.md), [infrastructure](docs/infra.md) |
| **Personal server** | The owner's own machine, running this same repository, reachable only through Cloudflare Tunnel + Zero Trust: repository hub, and later CI/CD and AI agents. | [personal server](docs/feat/personal_server.md) |
| **Work portal** | `/work`: a per-client page for messages, files, dashboards and receipts. Static shell today; backend is **not implemented** yet. | [work](docs/feat/work.md) |

What works today and what does not is tracked as checkboxes in **[docs/feat/README.md](docs/feat/README.md)**. In short: the public static site, themes, expertise timeline, desk with WASM shell, print layouts, Terraform/Worker routing and the signed read-only Git node work; client authentication, chat, receipts, dashboards and agents are not built. Personal Git pushes and Jazu CI/CD are implemented; see Server Use.

## Local Use

Build the website and view it on `localhost`. No cloud account needed.

**Requirements:** Node.js **22.18 or newer** (24 LTS recommended) and npm. Fonts are generated by TypeScript; nothing else is needed to build.

```sh
npm ci                                # install dependencies
npm run types                         # optional: TypeScript check
npm test                              # optional: contract tests
npm run check                         # optional: validate content (warnings are expected, see below)
npm run build                         # generate dist/
npm run serve -- --port 8080          # build, then serve http://127.0.0.1:8080
```

Open <http://127.0.0.1:8080>. `serve` builds first, so `build` before it is optional. The same commands work in PowerShell, cmd or a POSIX shell.

Handy variants:

| Command | Purpose |
|---|---|
| `npm run watch` | Rebuild when `content/`, `src/` or `config.json` change (restart after engine changes). Run next to `serve` while editing content |
| `npm run build -- --date 2026-11-04` | Pin "present" dates and font timestamps for a reproducible build |
| `npm run check -- --strict` | Also fail on editorial warnings |
| `npm run clean` | Remove `dist/` and `.cache/` |
| `npm run pack` | Write `codebase.zip` for sharing with AI agents (respects `.gitignore`; see the caveat below) |

Useful URLs: `/` (portfolio), `/desk` (desktop; enter `pid:` in a window's source field for a shell), `/projects`, `/blogs`, `/work`, `/ja/` (Japanese).

### Two things a fresh checkout may be missing

1. **WebAssembly artifacts.** `npm run build` bundles BusyBox, fastfetch, htop and TinyCC for the desk and needs `src/desk/busybox/artifacts/busybox.wasm`, `src/desk/programs/artifacts/{fastfetch,htop,tcc}.wasm` and their source archives. Those file types are git-ignored, so they are **absent from `codebase.zip`**. Restore them from the real repository/backup, or rebuild on Linux/WSL (needs network): see [docs/src/desk.md](docs/src/desk.md#artifacts).
2. **Media archive.** `content/media/` is git-ignored. Without it the build still runs but `check` reports each missing image/video. Restore the owner's archive there. Never put private documents in public content.

### Emulated cloud (optional)

To exercise the Worker, R2 range requests, KV and D1 locally with synthetic bindings (no credentials, no production effect):

```sh
npm run db:local        # apply migrations/*.sql to the local D1 (stored in ignored .wrangler/)
npm run serve           # terminal 1: static site on http://127.0.0.1:8080
npm run cloud:dev       # terminal 2: wrangler dev --config wrangler.local.jsonc
```

Wrangler serves the Worker on <http://localhost:8787> and proxies public HTML to `http://127.0.0.1:8080`. Try:

- <http://localhost:8787/api/v1/health> → `{"status":"ok","generation":12,"services":{"work":"not_implemented"}}`
- <http://localhost:8787/work> → the Work shell with `no-referrer`/`no-store`
- any other `/api/…` → `501` (unfinished APIs accept no data)

Optionally emulate the personal node's Git read API (**not verified in this environment**):

1. Copy `.env.example` to `.env`; set `ORIGIN_HMAC_SECRET` (≥ 32 random chars) and `JAZU_REPOSITORIES_JSON` to e.g. `{"stesis":"/path/to/a/public/clone"}`.
2. `npm run node -- --port 8788` in a third terminal.
3. Create `.dev.vars` (ignored) with `ORIGIN_HMAC_SECRET=<same value>` and `PERSONAL_ORIGIN=http://127.0.0.1:8788`, and set `PUBLIC_PROJECTS` in `wrangler.local.jsonc` to `"[\"stesis\"]"`.
4. Restart `cloud:dev`, then request <http://localhost:8787/api/v1/git/stesis/refs>.

`wrangler.local.jsonc` holds synthetic identifiers; **never deploy it**.

## Host Use

Build the resources and infrastructure and deploy the whole system to Cloudflare, using Terraform. Details of every resource: [docs/infra.md](docs/infra.md).

**You need:** a Cloudflare account; a domain whose DNS zone is on Cloudflare; Terraform ≥ 1.6; Node 22.18+ with `npm ci` done; the WASM artifacts and media archive from above; permission to publish the content (see the placeholders in [docs/README.md](docs/README.md#placeholders-the-owner-must-replace)).

### One-time setup

1. **Make it yours.** Edit `config.json`: `base_url`, `site_name`, `owner`, `deploy.pages_project`, `deploy.worker_name`, languages, `seo`. Replace the inherited identity/content listed in the placeholders table.
2. **API token.** Cloudflare dashboard → API tokens → create a token with *edit* on Workers Scripts, Workers Routes, Workers KV Storage, D1, R2 Storage and Cloudflare Pages, and *read* on Zone. Put it in `.env` as `CLOUDFLARE_API_TOKEN` (and the account id as `CLOUDFLARE_ACCOUNT_ID`).
3. **R2 S3 token.** R2 → Manage API tokens → create an access key (used only to upload large media).
4. **Inputs.** Copy `.env.example` to `.env` and fill `TF_VAR_account_id`, `TF_VAR_zone_id`, `TF_VAR_r2_access_key_id`, `TF_VAR_r2_secret_access_key` — or copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars`. `deploy` loads `.env` itself; a variable already exported in your shell wins. **Never commit `.env`, tfvars or state.**
5. **DNS.** Terraform creates the Worker routes `example.com/*` and `*.example.com/*` but **not DNS records**. Add proxied (orange-cloud) records for the apex and `*` in the dashboard (a dummy A record such as `192.0.2.1` is the usual placeholder, since the Worker answers the request). Check in the dashboard that both names resolve through Cloudflare.
6. **Existing account?** If resources already exist, import them before the first apply so Terraform adopts them instead of duplicating, e.g. `terraform -chdir=terraform import cloudflare_pages_project.site <account_id>/jazu`. Download an existing Pages project's real settings first.
7. **Deploying from more than one machine?** Configure a remote backend in `terraform/versions.tf` first; state is local by default and contains secrets.

### Deploy

```sh
npm run deploy:dry -- --date 2026-11-04               # build, stage Pages files, bundle the Worker; applies nothing
terraform -chdir=terraform init
terraform -chdir=terraform plan -var-file=<var_file printed in .cache/deploy/latest.json>
npm run deploy -- --target all                        # apply Terraform, then upload the Pages content
```

What `deploy` does: builds `dist/`; copies it to a staging folder, **excluding files over 25 MiB**, which are uploaded to R2 by Terraform; bundles the Worker with esbuild; writes a Terraform var-file; runs `terraform apply`; then runs `wrangler pages deploy` (Terraform has no resource for Pages direct uploads — the only remaining wrangler call).

| `--target` | Applies |
|---|---|
| `pages` | Pages project, large R2 objects, then uploads the Pages content |
| `worker` | Worker script, `workers.dev` subdomain, routes, D1 migrations (and their dependencies: bucket, KV, database) |
| `all` (default) | Everything, then uploads the Pages content |

Do not set `PAGES_ORIGIN` by hand: Terraform derives it from the Pages project (use `pages_origin` in `terraform.tfvars` to point at a preview deployment while testing).

### Verify

- `https://<your-domain>/` loads; `https://<your-domain>/api/v1/health` returns `status: ok`.
- `https://<your-domain>/assets/media/<a large file>` supports range requests (`206`).
- `https://<project>.<your-domain>` redirects (301) to `/projects/<project>` for each project id.

### Later

Re-run `npm run deploy -- --target pages` for content-only changes. The "present" date in timelines resolves to the build month, so rebuild monthly. Terraform manages only the objects in the current build; removing old R2 objects is up to you. Demo/work subdomains (`<name>-demo`, `<name>-work`) proxy only to explicit HTTPS origins stored in KV as `host:<name>-demo|work` and must not point back into your own domain.

*Status:* Terraform has not been validated against a real account yet ([feat/cloud.md](docs/feat/cloud.md)).

## Server Use

Set up the **personal server**: your own machine running an instance of this repository, connected to Cloudflare through a Tunnel protected by Zero Trust, so the public Worker can reach it securely and (later) your Git repository, CI/CD and AI agents can work on it. The public website never depends on it.

**What works now:** the loopback-only node answers HMAC-signed requests for health, read-only Git (`refs`, `tree`, `blob`, `log`) and, with a `server.json`, **git push** (per-user tokens), a static mirror so `git clone {domain}/projects/jazu` is served by Pages, and the **CI/CD pipeline of `jazu`** (push → tests → build → `wrangler pages deploy` only if the site changed). Every other project is archived: no pushes, no CI, no CD. **Not built yet:** dashboards, AI agents, SSH, pipelines for other projects ([status](docs/feat/personal_server.md), [design](docs/src/node.md#git-hub)). The git/CI parts are tested locally with real git but have not run on a real Cloudflare account.

1. **Install** Node.js 22.18+, Git and [`cloudflared`](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/). Clone this repository (the server is an instance of it) and run `npm ci`.
2. **Configure `.env`** (copy `.env.example`):
   - `ORIGIN_HMAC_SECRET` — ≥ 32 random chars: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
   - `JAZU_REPOSITORIES_JSON` — an explicit map of **public** project ids to local repository paths. **Never list a private/client repository** here.
3. **Run the node:** `npm run node -- --port 8788`. It binds `127.0.0.1` only; unsigned requests (including `/health`) return `401`. Supervise it (systemd, Task Scheduler, …) so it restarts, for example on Linux:

   ```ini
   # /etc/systemd/system/jazu-node.service  (example)
   [Service]
   WorkingDirectory=/srv/jazu
   ExecStart=/usr/bin/npm run node -- --port 8788
   Restart=always
   User=jazu
   [Install]
   WantedBy=multi-user.target
   ```
4. **Cloudflare Zero Trust** (dashboard → Zero Trust):
   1. *Networks → Tunnels:* create a tunnel, install the connector on the server, and add a **public hostname** (e.g. `node.example.net`) whose service is `http://127.0.0.1:8788`. Use a hostname that the Worker's wildcard route (`*.your-domain/*`) does not capture: a different domain, or a route exception for that hostname set to "no Worker".
   2. *Access → Applications:* protect that hostname with a **Service Auth** policy.
   3. *Access → Service Auth:* create a **service token**; keep its Client ID and Secret.
5. **Tell the Worker.** In `.env` set `ACCESS_CLIENT_ID` and `ACCESS_CLIENT_SECRET` (same `ORIGIN_HMAC_SECRET` as the node); in `config.json` set `"personal_server": "https://node.example.net"`. Then `npm run deploy -- --target worker`.
6. **Verify:** `https://<your-domain>/api/v1/git/<public_project_id>/refs` returns refs. With the node stopped it returns `503` — the rest of the site keeps working. Browser cookies/tokens are never forwarded to the node.

   Query parameters: `?ref=HEAD&path=readme.md`. Limits: 100 log entries; blobs ≤ 16 MiB; refs/paths cannot run arbitrary Git commands.

**Git hub and CI/CD setup** (after steps 1–6 above; `.env` also needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` for the deploy step):

```sh
node src/main.ts server init                          # writes server.json: set repos_dir, state_dir, site.dir (this checkout, on branch master)
node src/main.ts server repo init jazu                # bare repo + hooks
node src/main.ts server user add you --role owner     # prints your token once
git remote add server https://you:<token>@<domain>/projects/jazu.git && git push server master
node src/main.ts server status                       # queue and last runs; `server run` re-runs by hand
```

`site.dir` must be a normal clone on the deploy branch (it keeps the git-ignored WASM artifacts and `content/media`); the pipeline only fast-forwards it. Collaborators: `server user add friend --role write` (branches only; owners merge). Existing archived repositories: put them in `projects` in `server.json` (`path` to a bare repo) and they are mirrored read-only. Also add `<project id="jazu">` to `content/` (included) so the Worker treats it as public.

**Using the server as the build/deploy machine manually (no pipeline).** The server may also run `git pull && npm ci && npm run deploy -- --target all`. That machine then needs Node, Terraform, `npm ci`, the same `.env`, **and the Terraform state** (use a remote backend).

**Planned:** SSH transport, AI agents, dashboards and pipelines for projects other than Jazu. HTTPS Git transport, contributor tokens and the Jazu push pipeline are implemented.

## Desk Use

Run the desk as a **full desktop**: the machine boots to an X session whose only program is Chromium showing `/desk`, and a terminal window there is a **real shell on the machine**, not the WebAssembly one.

```
Chromium (--app, full screen) → http://localhost:8080/desk
        ↕ JAZU extension (extension/)            only on the exact localhost origin you allow
        ↕ native messaging host (extension/host)  Node + a pty, started by Chromium, no network port
        your shell on the device
```

Design decisions:

- The site is served from **`localhost`**, never from the real domain: the bridge to the shell must not be reachable from a public website. (`npm run serve` binds `127.0.0.1`; `localhost` is also a secure context, which the File System Access API needs.)
- The extension is the only way in. It runs on `http://localhost/*`, accepts only origins listed in `extension/allowed_origins.json` (default `http://localhost:8080`), and Chrome starts the host only for this extension's fixed id.
- Without the extension nothing changes: `/desk` keeps its WebAssembly shell, and `pid:` always opens it, even with the bridge present.

Setup on the kiosk machine (Debian, no desktop environment: `xinit`/`startx`, an X server such as `xserver-xorg`, `chromium`, Node 22.18+, `python3`):

```sh
git clone <your repo> /opt/jazu && cd /opt/jazu
npm ci && npm run build
npm run extension:install -- --origin http://localhost:8080 --user-data-dir ~/.config/jazu-desk
cp extension/xinitrc.example ~/.xinitrc     # edit JAZU_DIR / PORT
startx                                      # or: xinit ~/.xinitrc -- :0 vt1
```

Use **Chromium** (or Chrome for Testing): branded Google Chrome removed `--load-extension` in version 137. Full guide, protocol, threat model and troubleshooting: [extension/README.md](extension/README.md). Status: [docs/feat/desk_env.md](docs/feat/desk_env.md). The host and the page-to-host chain are covered by `tests/host.test.ts` and `tests/host_bridge.test.ts`; running it inside a real Chromium/X session has **not** been verified yet.

### Personal-server production configuration

The checked-in `wrangler.production.jsonc` routes `jasouza.com/*` to `jazu_router`, serves static output from `jazu.pages.dev`, and uses `personal-server.jasouza.com` for signed origin requests. It deliberately leaves existing unrelated subdomain services intact. The origin hostname must have a Tunnel ingress to `http://127.0.0.1:8788` and an Access Service Auth policy allowing only the Worker's service token. `/api` returns discovery JSON; `/api/v1/ci/jazu/runs` reports deployment status.

Worker updates are an operator action (CI deploys Pages only):

```sh
node --env-file=.env node_modules/wrangler/bin/wrangler.js deploy --config wrangler.production.jsonc
# Upload ORIGIN_HMAC_SECRET, ACCESS_CLIENT_ID and ACCESS_CLIENT_SECRET using wrangler secret bulk.
# Never pass the entire .env: the Worker does not need the Cloudflare API token.
```

Use `ops/jazu-node.service.example` as the systemd service, adjusting the user, checkout and Node paths. The node must run with Node 22.18+; Node 24 is recommended. Keep `build/` WASM artifacts and `content/media/` in the checkout: CI restores these ignored inputs into its isolated clone. Keep `server.json`, `.env` and state private and backed up.

For a hub that accepts `git push origin master` while this feature is developed, set `site.branch` to `master` and `site.checkout_branch` to `feature/personal-server`. The hub's bare `master` is seeded from this feature branch; the server's working checkout stays on the feature branch. The GitHub remote remains the source backup and is separate from the personal Git hub.

```sh
git clone https://jasouza.com/projects/jazu
cd jazu
# Git prompts for the collaborator username and token on the first push.
git push origin master
```

Create tokens on the Pi with `node src/main.ts server user add <name> --role owner` (trusted deployers) or `--role write` (contributors who push review branches). Owners can push master and execute CI code on the Pi. Tokens are separate from SSH passwords and Cloudflare credentials. Store tokens in your Git credential manager. Public clones continue working when the Pi is stopped; pushes and origin-backed APIs return an unavailable response.

The production resources provisioned for this branch use Wrangler and the Cloudflare API. Import them into Terraform before using `npm run deploy`; no Terraform state was created by this setup. Large assets over the Pages limit must be uploaded to `jazu-assets` at their generated `assets/media/...` or `assets/wasm/...` keys before publishing, and again when those assets change.
