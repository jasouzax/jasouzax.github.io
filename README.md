# JAZU · generation 12

JAZU is a file-authored portfolio and browser workspace. Generation 12 migrates the generation-11 engine and content into this repository root. `COMPONENTS.md` is the architecture contract; `TASKS.md` records what actually works and what remains. The cloud client portal and full plugin architecture are still development work; the public static site works independently.

## Local use

Requirements: Node.js 22.18+ (24 LTS recommended), npm, the dependencies installed by npm. Font binaries are generated by TypeScript under `src/font`.

```powershell
npm ci
npm run types
npm test
npm run check
npm run build
npm run serve -- --port 8080
```

Open http://localhost:8080. `serve` builds first. For content edits run `npm run watch` in another terminal. Pin a build date with `npm run build -- --date 2026-11-04`. `npm run check -- --strict` also fails on editorial warnings. `npm run clean` removes only generated output and caches. No gen-11 checkout or dependencies are needed at runtime.

The supplied media was ignored by gen-11's Git repository. It has been copied locally into `content/media`, which stays ignored. Website-specific SVG assets are tracked in `content/assets`. A fresh clone needs the owner's media archive restored there; missing files are reported by `check`. Never place private documents in public content. See `PLACEHOLDER.md` before publishing.

## Content ownership and resource paths

The content team controls all folders inside `content/`. The engine recursively discovers XML by root tag, so pages, blogs, themes, plugins and other roots can live together or anywhere in that tree. No source changes are needed when these folders are renamed. Relative XML resource references resolve from the XML file that declares them; references beginning with `/` resolve from the content root. Theme styles and plugin inputs also follow their declaring XML files.

Website-wide artwork is declared in `config.json`, with paths relative to `content/` (a leading `/` is optional):

```json
{
  "resources": {
    "signature": "/assets/signature_animation.svg",
    "icon": "/assets/signature.svg",
    "favicon": "/assets/favicon.svg"
  },
  "pack": {
    "exclude": ["content/media"]
  }
}
```

`signature` is the animated header/loading artwork. `icon` supplies Apple/PWA icons and generated link-preview covers; it falls back to the configured signature, then favicon. `favicon` overrides the generated browser-tab SVG and ICO. Empty paths disable that input; there are no implicit filename or folder searches. Files must remain inside `content/`, including symlink targets. Configured paths participate in rebuild tracking.

`pack.exclude` contains project-relative files or directories to omit from source archives; it defaults to an empty list. When renaming a folder, update its XML references, any matching config paths/exclusions, and the content team's `content/.gitignore` entries. Generated URLs such as `/assets/media/…`, `/icon.svg` and `/srv/blogs/…` belong to the website's output protocol and do not depend on source folder names. Unreferenced content files remain unpublished.

## Find and edit things

| Location | Purpose |
|---|---|
| `config.json` | Public owner/site settings, languages, theme selection, icon registry, deployment names |
| `content/` | XML roots and resources in any folder layout; language variants may share one XML file |
| `content/blogs/`, `content/media/`, `content/theme/` | Current content-team conventions for articles, local media and themes; names are not engine requirements |
| `content/assets/` | Current location of tracked website artwork, selected through `config.json.resources` |
| `src/main.ts`, `src/commands.ts` | TSX loader entry point and CLI commands |
| `src/model.ts`, `objects.ts`, `schema.ts`, `xml.ts` | Discovery, object generators, validation and parsing |
| `src/build.ts`, `cache.ts`, `graph.ts` | Build orchestration and incremental output |
| `src/web/` | TSX generators, virtual-node rendering, print layouts, SEO and TSX partials |
| `src/web/client/` | SPA, search, theme switching, browser filesystem, processes and desk windows |
| `src/node/` | Local serving and cloud/origin adapters |
| `src/desk/` | BusyBox WASM toolchain, prepared binaries and browser process port |
| `src/font/` | Node.js OpenType table writer and WOFF/WOFF2 packaging |
| `tests/` | Migration contract regression tests |
| `dist/`, `.cache/` | Generated, disposable files |
| `gen-11/` | Ignored source reference; never import from it |

XML filenames and folders do not choose routes. `<page path="/">` defines a page; `<project id="example">`, `<event id="example">`, and `<blog id="example">` generate their own pages. Keep translations together: a single file contains one `<page path="…" lang="en">` and one `<page path="…" lang="ja">` for the same route. Blog translations likewise share a file. A file may contain several roots. `<expertise>` declares the skill/stack vocabulary; entries come from project and event roots. `<hero tab="Home" name="…">` overrides the head-tab label while preserving the visible hero name. `<hero>` replaces landing/contact; `<item>` holds contact links. Desks use `<menu>` and `<window mode="view|edit">`. A root `<print name="resume">` supplies print styles; a page selects it with `print="resume"`. Print personal information comes only from the landing hero and its labelled items.

Projects keep shared metadata such as name, date and role. Action links (`website`, `source`, `paper`, `event`) and custom `<action>` children also belong to `<project>`. Their buttons stay visible while the media, description and hashtags crossfade between skill variations. Put `skill` and `info` on their child slides. A slide's comma-separated `skill` list selects the expertise views that render that version; each skill can belong to only one public slide per project. `description` remains supported as an alias for slide `info`, followed by inline text as a fallback. A featured project uses its `featured="true"` slide (or its first public slide) in Featured, page summaries and the generated project desk. Each project occupies one carousel slide, dot and timeline marker; its authored slides become variations within that position. The footer lists all the project's slide skills; choosing one crossfades the content in place and changes the fragment, for example from `#web-app/gdsc` to `#cloud/gdsc`.

```xml
<project id="example" name="Example" date="Jan 2026" featured="true" website="https://example.com">
    <slide skill="web-app" info="Interface and design work." stack="vue, vuetify"/>
    <slide skill="cloud" info="Backend and database work." stack="firebase"/>
</project>
```

UI translations are string dictionaries at `config.json.languages.en.<id>` (and `languages.ja.<id>`).

Shared layout is emitted inline from the unnamed theme in `content/theme/layout.xml`. Its `scope="layout"` source extracts geometry from the legacy Sass after the content-dependent expertise selectors are generated; the remaining paint is scoped to Default. Other unnamed styles are inlined as written. Named skins inherit the low-priority `layout` CSS layer and can override geometry directly. Memory supplies its own skin without importing Default. Shared role-label behavior lives in `content/theme/roles.scss`.

`src/web/skeleton_css.ts` supplies the light/dark loading overlay and `src/web/client/loading.ts` coordinates initial loading, SPA wipes and theme changes. Inline boot captures fixed placeholder rectangles before the theme activates, so fonts and theme geometry cannot move the skeleton. Each placeholder uses a separate moving shine layer. Once resources settle, complementary diagonal masks remove the placeholders and reveal the content while the neutral backdrop fades into the theme color; the background renderer starts afterward. Content already in view skips its entrance animation. Theme CSS loads without blocking the skeleton; visible images and fonts receive a bounded readiness wait before reveal. Page swaps preserve the existing signature SVG. Theme changes pass through the neutral layout, remove the previous font stylesheet, and restore the previous theme on failure. Reduced motion and paused motion stop shimmer/wipes; no-JavaScript pages use ordinary stylesheet links. Inline CSS has a generated CSP hash. Run `npm run build` followed by `npm run test:loading:browser` to verify the loading lifecycle.

Relative resources resolve from their XML file. Referenced resources are published; arbitrary files under content are not copied. Browser `/home/user` belongs to the visitor. `/srv` contains public published resources. New uploads belong in `/tmp`. Planned server persistence is not implied by a static menu URI.

Generated project desks open and focus `/srv/projects/{id}` by default. New folder windows and terminals start there, with commands available from `/bin`. `/home/user` remains the visitor's virtual filesystem or connected folder; the shell's `HOME` stays `/home/user`, so `cd` returns there.

A project can contain one `<research>` block to generate an **Overview** menu with these sections, in order: `<terminology>`, `<problem>`, `<solution>`, `<significance>`, `<objectives>`, `<literature_review>`, `<frameworks>`, `<methodology>` and `<results>`. Write each section's explanation as body text. Except for Terminology, sections may contain nested `<point name="…">Explanation<point name="…">More detail</point></point>` elements. These are expandable explanations with no links, file-opening behavior or action buttons. The English `stesis` project in `content/projects.xml` contains a complete placeholder reference; its literature prompts and results are not verified research.

The account menu's **Connect with Folder** mounts a chosen local folder at `/home/user` through the File System Access API. Existing home entries are copied into it; collisions receive ` (N)` before the extension, and existing directory trees stay intact. Originals remain in private storage as a backup. New files, editor saves, uploads, moves, deletes, shell writes, and preview caches then use the chosen folder directly. Connections are remembered in IndexedDB; a browser may require selecting the folder again to renew access. Missing permission disables file creation instead of falling back to a stale private-storage copy. Browsers without the directory picker show the action disabled. Local folder access requires a secure context, such as HTTPS or localhost.

## Cloudflare and private nodes

Pages serves generated HTML/CSS/scripts. The central Worker handles `/api`, public R2 media/WASM, subdomain rules and the `/work` shell; public pages continue working if the personal node is offline. The private node currently supports signed health and public Git **read** operations, not pushes, dashboards or agents. Client authentication/chat/receipts remain unchecked in TASKS.md; those APIs return `501` and accept no client data.

Start locally without cloud credentials:

```powershell
npm run db:local
npm run cloud:dev
```

In a separate terminal run `npm run serve`. Wrangler exposes the Worker at http://localhost:8787 and proxies public HTML to http://127.0.0.1:8080. Inspect http://localhost:8787/api/v1/health. Local D1/R2/KV data is in ignored `.wrangler/`. Local migrations have no production effect.

Prepare a deployable site and bundle the Worker, without uploading or applying anything:

```powershell
npm run deploy:dry -- --date 2026-11-04
```

This builds `dist`, bundles the Worker to a single ES module with esbuild and writes `.cache/deploy/latest.json`, which points to the Pages staging folder, the Worker bundle, a generated Terraform var-file and the R2 upload list. Files over 25 MiB are excluded from the Pages staging directory and uploaded to R2 by Terraform. XML media URLs are content-hashed under `/assets/media/`; the Worker serves large files with range support and falls back to Pages for small assets. Six supplied videos need R2. Referenced media is copied locally; unreferenced media is not published.

### Infrastructure as code (Terraform)

All Cloudflare infrastructure lives in `terraform/`: the Pages project, R2 assets bucket, KV registry, D1 database, the Worker script with its bindings and secrets, the apex and wildcard routes, the `workers.dev` subdomain, large-media R2 objects, and D1 migrations. Wrangler is no longer used to provision or deploy these.

One-time setup:

1. Install Terraform >= 1.6.
2. Create a Cloudflare API token with edit permission for Workers Scripts, Workers Routes, Workers KV, D1, R2, Pages and Zone read, and export it as `CLOUDFLARE_API_TOKEN`. D1 migrations reuse the same token.
3. Create an R2 S3 API token (R2 > Manage API tokens) for uploading large media.
4. Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars` and fill in `account_id`, `zone_id` and the R2 keys. Set the Worker secrets (`origin_hmac_secret`, `access_client_id`, `access_client_secret`) there when the personal node exists. This file is git-ignored; never commit it or the state.
5. For an existing, already-provisioned account, import resources before the first apply (for example `terraform import cloudflare_pages_project.site <account_id>/jazu`) so Terraform adopts them instead of creating duplicates. Download an existing Pages project's actual settings first.

Plan, then deploy:

```powershell
npm run deploy:dry -- --date 2026-11-04
terraform -chdir=terraform init
terraform -chdir=terraform plan -var-file=<var_file from .cache/deploy/latest.json>
node src/main.ts deploy --target all
```

`--target pages` applies the Pages project and large R2 objects, then uploads the Pages content; `--target worker` applies the Worker, routes and D1 migrations (using Terraform `-target`, which also applies required dependencies such as the bucket, KV namespace and database); `all` applies everything, then uploads the Pages content. Do not set `PAGES_ORIGIN` by hand: Terraform derives it from the Pages project, or use `pages_origin` in `terraform.tfvars` to point at a preview deployment while testing. The generated Worker variables include **only public project ids** for subdomain redirects. KV records `host:<name>-demo` and `host:<name>-work` contain explicit external HTTPS origins; unknown hosts return 404. Those registry origins cannot point back into the same public domain because that would loop through the Worker.

Known limitation: Terraform has no resource for Pages direct-upload deployments, so the final Pages content upload still shells out to `wrangler pages deploy` (the only wrangler call left in the deploy path). Local development also still uses `wrangler dev` with `wrangler.local.jsonc`. D1 is a schema foundation; provisioning it does not enable the unfinished Work APIs. Deleting old R2 objects is an owner retention task; Terraform only manages the objects listed in the current build, so removed media is left in the bucket until you delete it.

Set up a personal node:

1. Install Node/npm and Git, clone this branch and run `npm ci`.
2. Copy `.env.example` to `.env`. Generate a high-entropy `ORIGIN_HMAC_SECRET` of at least 32 characters. Set `JAZU_REPOSITORIES_JSON` to an explicit map of **public** project ids to local repository paths. Never include a private/client repository in this public read adapter.
3. Run `npm run node -- --port 8788`. It binds loopback only. Unsigned requests, including `/health`, return 401. The Git adapters support refs/tree/blob/log (100 log entries; blobs capped at 16 MiB). Ref/path queries cannot invoke arbitrary Git commands.
4. Create a Cloudflare Tunnel with a private origin hostname pointing to `http://127.0.0.1:8788`. Protect that hostname with a Cloudflare Access **Service Auth** policy and a service token. Keep it distinct from the central Worker's wildcard public domain routes.
5. Set `config.json.personal_server` to that HTTPS origin. Store the same HMAC key in the Worker by setting `origin_hmac_secret` in `terraform/terraform.tfvars`; likewise set `access_client_id` and `access_client_secret` from the Access service token. Then run `node src/main.ts deploy --target worker`.
6. Supervise the node and cloudflared with the operating system's service manager. The HMAC covers method, path/query, timestamp, nonce, client and body hash; the origin rejects expired/replayed signatures. If it is offline the public Git API returns 503. Snapshot dashboards and native Git clone/push transport are future tasks.

For `GET /api/v1/git/<public_id>/{refs|tree|blob|log}`, use `?ref=HEAD&path=readme.md` as needed. Browser cookies/tokens are never forwarded to this node. `/desk` is browser-local and does not upload visitor files to it.

Cloudflare references: [Cloudflare Terraform provider](https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs), [Pages commands and configuration](https://developers.cloudflare.com/workers/wrangler/commands/pages/), [Pages limits](https://developers.cloudflare.com/pages/platform/limits/), [R2 uploads](https://developers.cloudflare.com/r2/objects/upload-objects/), [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/), [Access service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/).

## Development and review

Work only on `migration/gen-11-to-gen12`. At each successful state update the task checkboxes and commit using Conventional Commits, for example `refactor(content): migrate object roots`. Run types, contract tests, content checks and a production build for changes affecting generation. Warnings are actionable content findings and are not suppressed to make the migration look complete. The owner reviews and merges to master manually; no deployment or merge is part of this migration.

## Validation and current limits

The migration is validated locally with 22 regression tests, TypeScript checking, 68 generated routes, local HTTP smoke checks, a Wrangler Worker bundle dry-run, and a local D1 migration. A real Wrangler local R2 range request returns `206` with the requested bytes. Repeating a build with the same date and unchanged sources skips all 68 pages and writes zero files. The portfolio and desk were also inspected in a browser. No production credentials, deployment or master merge were used.

The content validator currently reports 39 warnings: the missing Hypro image in two languages and 37 inherited SEO description-length findings. These are recorded in PLACEHOLDER.md; `check --strict` deliberately fails until they are resolved. The public media archive must be restored for a fresh clone.

The migration delivers a runnable generation-12 foundation. The full target architecture is not finished: the shared vnode engine, timestamp/HEAD source cache, shared fixed-canvas theme contract, complete plugin/WASM pipeline, radio-based expertise filters, consistent browser /srv mounts and authenticated Work services remain unchecked in TASKS.md. Inline skeleton loading is implemented; existing desk viewers and theme background renderers remain in use during that transition. Node font output is reproducible for a pinned build date.
